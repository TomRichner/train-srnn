# Overnight 700-epoch runs — LR + closed-loop α schedules

> **Update**: the LR-warmup-shadowing bug described below has since been
> fixed in `train.py`'s scheduler setup. The continuous trainer now sizes
> `total_steps` and `warmup_frac` against its own per-chunk cadence, and
> `warmup_epochs` defaults to `round(B/2)` (24 epochs at B=48), surfaced
> as a `warmup_epochs` config key for explicit override. The discussion
> below is preserved as the historical analysis of what *did* run on the
> overnight 700-epoch jobs (commits prior to the fix).


Reconstructed from `conf/config.yaml`, `conf/task/seeg.yaml`, and the
`scripts/overnight_run.sh` overrides (`epochs=700 batch_size=48 amp=bf16
lr=5e-4 closed_loop.enabled={false,true} ${ABLATIONS}`). All other knobs
came from `conf/config.yaml` defaults, including `cosine_decay=false` and
`grad_checkpoint_segment_len=5`.

Plots generated by [`_make_plots.py`](_make_plots.py).

## 1. LR schedule

There **was a brief warmup**, but it's so short it's invisible at the
checkpoint-cadence sampling rate of `lr_schedule.png` from the
postprocess pipeline. Drilling in:

![LR schedule](lr_schedule.png)

**Numbers driving the warmup length:**

| Quantity | Source | Value |
|---|---|---|
| `cfg.lr` (max_lr) | `scripts/overnight_run.sh` override | `5e-4` |
| `cfg.epochs` | override | `700` |
| `cfg.batch_size` | override | `48` |
| `len(train_x)` (windowed view) | `train_srnn/data/datasets.py:_window` | `141` |
| `steps_per_epoch` (train.py:425, **windowed**) | `141 // 48 + 1` | **`3`** |
| `total_steps` (train.py:426) | `700 * 3` | **`2100`** |
| `warmup_frac` (train.py:428) | `min(2*3/2100, 0.2)` | `0.00286` |
| `warmup_end` in scheduler.step() calls | `int(2100 * 0.00286)` | **`6`** |
| `start_lr` | `WarmupHoldCosineSchedule` default | `1e-8` |
| `cosine_decay` | `cfg.get("cosine_decay", False)` | `False` |

**The shadowing bug** (also documented when we last looked at this):
`train.py` builds the scheduler using `total_steps = epochs *
windowed_steps_per_epoch`, but the **continuous trainer** calls
`scheduler.step()` at its own cadence — `15` per epoch (computed from
`(T + B·chunk_len − 1) / (B·chunk_len) = (179989 + 11999) / 12000`).
Over 700 epochs the scheduler is actually stepped `700 × 15 = 10,500`
times, but it was *configured* expecting only `2100` total steps.

Trajectory in practice:

| Phase | Steps (real `scheduler.step()` count) | Epoch range | LR |
|---|---|---|---|
| Linear warmup | 0 → 6 | 0 → 0.4 | `1e-8` → `5e-4` |
| Hold at `max_lr` | 6 → 10500 | 0.4 → 700 | **`5e-4` (constant)** |

So warmup completes by epoch ~0.4, and lr is constant at `5e-4` for the
remaining ~99.94% of the run. There is no cosine tail because
`cosine_decay=false` in `conf/config.yaml`. The "Phase 2" branch of
`WarmupHoldCosineSchedule.get_lr()` (line 58–60 in `lr_schedule.py`)
explicitly handles `not self.cosine_decay` by holding at `max_lr` even
past the nominal `hold_end`, so the past-`total_steps=2100` extension
is also harmless — lr just continues at `5e-4`.

**Spike-toward-end loss instability** the user observed is therefore
**not** a scheduled-LR-decay artifact (there isn't one). It's a noise
event under the constant-`5e-4` regime.

**Why the postprocess `lr_schedule.png` looks dead-flat**: that plot
samples at `checkpoint_interval` epochs (= `round(B/4) = 12` for
`B=48`). The first sample lands at epoch 12, well past the 0.4-epoch
warmup. Every sample shows `5e-4`. The plot is accurate; the warmup is
just below its sampling resolution.

## 2. Closed-loop α schedule (run 2)

Run 2 (`overnight-run2-Whoist-cl`) used `closed_loop.enabled=true` with
all other closed-loop knobs at `conf/config.yaml` defaults. The full
formula in `train_srnn/training/closed_loop.py:sample_continuous_alpha`
is:

```
α[b, t, c] = envelope(t) · clip(baseline_b + rnd[c], 0, 1)
```

For our defaults the formula collapses dramatically. Each component:

| Component | Default | Effect in run 2 |
|---|---|---|
| `alpha_baseline` | `0.3` | scalar baseline |
| `alpha_baseline_start` | `null` | **no run-time ramp** — baseline stays `0.3` from epoch 0 to 700 |
| `alpha_baseline_jitter` | `0.0` | no per-reader uniform offset (`baseline_b ≡ 0.3` for all readers `b`) |
| `alpha_rnd_density` | `0.0` | per-channel sparse Gaussian disabled — `rnd[c] ≡ 0` |
| `alpha_rnd_sigma` | `0.0` | (irrelevant when density=0) |
| `alpha_rnd_period_epochs` | `10` | per-channel rotation `sin²(π·(epoch/10 − φ_c))` is **scaled by `alpha_rnd_sigma=0`**, so rotation has no effect |
| `t_warm` | `2500` | half-cosine ramp; **windowed-mode only — IGNORED in the continuous trainer** |
| `teacher_forcing_batch_frac` | `0.2` | each *chunk* (training step) is a coin-flip pure-TF (`α=0` everywhere) with prob 0.2 |

So the effective schedule is binary, per chunk:

```
α = 0    with prob 0.2   (pure teacher forcing)
α = 0.3  with prob 0.8   (constant 0.3 for every reader, every channel, every timestep)
```

No within-epoch ramp, no within-channel variation, no per-reader scatter.

![alpha schedule](alpha_schedule.png)

**Sanity check vs. logged stats from epoch 699:**

| Stat | Logged | Predicted from formula |
|---|---|---|
| `alpha_mean` | `0.240` | `0.3 × (1 − 0.2) = 0.240` ✓ |
| `alpha_max` | `0.300` | `0.3` ✓ |
| `pure_tf_frac` | `0.200` | `0.2` ✓ |

Every value matches. No surprises in run 2's α statistics.

**What this means for the loss trajectory**: closed-loop in run 2 was a
"flat 30% feedback, with 20% of chunks forced fully open-loop". It
wasn't doing per-channel rotation or per-reader scatter or any kind of
warm-up curriculum. The baseline jumps from 0 (open-loop teacher
forcing in run 1) to 0.3 (run 2) on the first chunk and stays there.

If we want a more nuanced closed-loop curriculum next time, the levers
to flip are:
- `alpha_baseline_start: 0.0` (or lower) → linear ramp from
  `start → alpha_baseline` over `total_epochs`.
- `alpha_baseline_jitter: 0.05` → readers see different α each epoch
  (uniform half-range).
- `alpha_rnd_density: 0.05–0.2` and `alpha_rnd_sigma: 0.05–0.15` →
  per-channel sparse Gaussian, makes some channels go closed-loop on
  some epochs and not others; the per-channel period is
  `alpha_rnd_period_epochs` (default 10).

## Resume runs at lower LR

If we kick off a 150-epoch resume from `last.pt` of each run with
`lr=1e-4`, the scheduler trajectory becomes:

| Quantity | Resume run |
|---|---|
| `cfg.lr` | `1e-4` |
| `cfg.epochs` | `150` |
| `total_steps` (train.py) | `150 × 3 = 450` |
| `warmup_frac` | `min(6/450, 0.2) = 0.0133` |
| `warmup_end` | `int(450 × 0.0133) = 5` |

**However**, `init_ckpt` resume restores the scheduler's `last_epoch`
(`train.py:462`, `load_checkpoint(scheduler=scheduler)`) — so on the
first scheduler.step() of the resumed run, `last_epoch` jumps from
`10500` (end of original) to `10501`. That immediately satisfies
`step >= warmup_end (=5)` and falls into the Phase 2 hold branch,
returning `max_lr = 1e-4`. **No warmup applied to the resume.** Adam's
moment estimates and step counters are also fully restored, so the
optimizer continues with its built-up state at the new (lower) LR.

For the closed-loop resume, α schedule is recomputed fresh from
`cfg.seed` + the *new* local epoch counter (0 → 149), so technically
the "epoch 0" α realization differs from where run 2 left off — but
since the distribution is constant (`alpha_baseline=0.3`,
`pure_tf_frac=0.2`), the *statistics* are continuous across the seam.
At default `alpha_rnd_period_epochs=10`, even the per-channel rotation
phase happens to align (700 mod 10 = 0), so there's no discontinuity
visible in the rotation either — though that whole rotation term is
scaled by `alpha_rnd_sigma=0` and contributes nothing anyway.
